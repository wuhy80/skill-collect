# Git 提交规范

让未参与开发的人仅阅读提交说明，就能理解为什么要改、解决了什么问题或补齐了什么能力，以及改后有什么效果。编写、检查和执行提交都使用本规范；是否执行提交、是否允许修改历史，以及测试、推送和部署要求，遵循当前用户指令与仓库规则。仅要求推荐或润色提交说明时，输出建议即可，不因此创建提交。

## 先确认实际提交范围

- 在实际所属仓库内读取适用的 `AGENTS.md`，检查 `git status --short`、未暂存差异和已暂存差异，识别任务开始前已有的修改。多个独立仓库分别提交。
- 仅暂存本轮明确属于当前目的的文件或片段，保留用户及并发任务的修改。不要用全仓暂存、格式化或清理混入无关内容；除任务明确需要外，不纳入无关锁文件和安装副产物。
- 一个提交只表达一个清晰目的；必要的实现、测试和配套文档可以合并。无关功能或重构应拆分。不要仅为了匹配类型而把同一修复和它的回归测试拆开。
- 根据仓库要求完成与改动风险相称的验证。纯提交说明或规则文档调整以内容核对为主，不因此新增业务测试或重启服务。

## 标题格式

```text
<type>(可选 scope): 中文说明
```

- `type` 使用下表中的小写英文类型，以提交的主要目的为准。
- `scope` 使用稳定的模块名称，如 `pms`、`auth`、`workflow`、`objectset`。范围没有额外信息时可省略；避免长文件路径和为每次提交临时造名称。
- 描述使用中文，保留必要的技术标识，使用“新增、支持、修复、限制、移除、统一”等明确动词，优先说明实际问题或调用方获得的能力，避免只写新增了某个接口、解析器或内部机制。
- 标题保持一行，尽量控制在约 50 个字符内，以清楚为先，不机械截断，也不默认附加句号。
- 不使用“修复问题”“优化代码”“更新功能”“完成修改”等缺少具体含义的标题，不使用日期或文件清单代替改动目的。

| 类型 | 用途 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `refactor` | 重构代码，保持外部行为一致 |
| `perf` | 性能优化 |
| `docs` | 文档修改 |
| `test` | 新增或调整测试 |
| `build` | 构建方式、依赖或打包配置修改 |
| `ci` | 持续集成流程修改 |
| `chore` | 工具配置、维护等其他改动 |
| `revert` | 撤销已有提交 |

示例仅说明格式，实际说明必须来自当前差异：

```text
fix(pms): 使用已保存的业务人员映射查询个人任务
feat(workflow): 支持复制已有工作流节点
refactor(objectset): 统一 Pipeline 根字段构造逻辑
docs: 补充插件部署后的核查步骤
```

## 讲清问题与结果，按需增加正文

每条提交都必须交代改动的实际目的和结果。标题已经说明清楚的简单改动可以只有标题；无法从标题直接理解为什么要改、解决什么问题或补齐什么能力时，必须增加正文，标题与正文之间空一行。按实际改动说明：

- 问题或需求：缺陷说明什么场景下原行为会导致什么问题；新功能说明哪类用户或调用方在什么场景下缺少什么能力；重构、性能或维护改动说明实际存在的维护、性能或交付障碍。
- 修改后的行为，以及影响的调用方或公共契约。
- 理解改动所需的关键实现或约束，按需补充。
- 实际执行的验证命令和结果；未完成的关键验证如实标明。

正文先讲问题或能力缺口，再讲改后结果，最后按需补充实现与验证。“复用成员图、严格分页、校验 JWT”等实现清单不能代替问题说明；测试通过也不能说明为什么要改。问题与效果须来自用户需求、实际差异及必要的原实现核对，不能仅凭函数名推测，也不能为新功能编造历史故障或未经验证的收益。

正文不必套固定模板或罗列所有函数，不把未经运行的测试写成“通过”，不把本地验证写成真实环境验收。

```text
fix(objectset): 移除 Pipeline 请求中的根级分页字段

预览传入分页参数时，原实现会向 Pipeline 请求追加根级 page，
导致请求违反 ObjectSet 契约。

分页改由 Pipeline 节点表达，预览与保存复用同一根字段构造逻辑。

验证：相关回归测试通过，ObjectSet 严格契约校验通过。
```

新增能力也要交代使用场景与原有缺口，例如：

```text
feat(workflow): 支持审批按当前用户权限解析角色参与人

iWorkDT 审批需要将角色解析为参与人，原有入口要求通知专用 Key，
缺少使用当前用户登录态调用的入口。

新增用户 JWT 入口，校验调用者的角色与主体目录读取权限后返回角色成员。

验证：工作流与通知定向 Go 测试通过；未做真实数据库与审批联调。
```

确实存在已获授权的不兼容公共变更时，在类型或范围后加 `!`，并使用 `BREAKING CHANGE:` 正文页脚说明影响和调用方需要的调整。标记不兼容不代替仓库要求的审核或授权，也不用于推断产品已经发行。

```text
feat(api)!: 调整对象查询响应结构

BREAKING CHANGE: 查询结果字段由 items 调整为 objects，
调用方需要更新结果读取逻辑。
```

## 提交前核对与执行

每次提交都核对最新暂存差异，即使同一会话已经使用过本 skill：

1. 用 `git diff --cached --stat` 和 `git diff --cached` 确认实际文件、片段与本次目的相符；对已暂存的用户修改逐项识别，不能默认一起提交。
2. 用 `git diff --cached --check` 检查空白错误，并核对所需验证已完成；不通过时修复本轮问题，不能弱化测试或校验来完成提交。
3. 逐项核对类型、范围、标题和正文与实际差异一致，并检查：未参与开发的人只看说明，能否知道什么场景下存在什么问题或能力缺口，以及改后有什么效果？若只能读到“新增解析器、复用模块、增加校验、测试通过”等实现与验证信息，必须补清问题和结果后再提交。发现多个无关目的时调整暂存范围或拆分提交，而不是扩大标题掩盖问题。
4. 确认差异和提交说明不含 token、密码、API Key、短期票据或带凭据 URL；不要把敏感值输出到聊天、日志或临时提交说明文件。
5. 已有提交授权时执行本地提交；多行说明优先写入临时文件，通过 `git commit -F` 使用，保留实际换行并正确引用 shell 参数，使用后清理临时文件。不要用会执行反引号或命令替换的字符串拼接生成说明。
6. 提交后回读实际 SHA、说明、提交文件和工作区状态，确认没有混入其他改动；适用仓库要求的额外审核仍须执行。执行 amend、squash 或冲突解决后，重新核对最终差异与说明；本 skill 不授权改写历史。

使用本 skill 不自动授权推送、同步运行目录、打包、部署或重启。交付时如实说明本地提交及验证结果。
